## 2) Backend (api/) — Components, endpoints, and responsibilities

### 2.1 Backend entry point and lifecycle
File: `api/main.py`

On startup (lifespan):
1. Loads env (`.env`)
2. Enforces `GROQ_API_KEY` is set
3. Runs database migrations:
   - `run_alembic_upgrade()` triggers `alembic upgrade head`
4. Initializes PostgreSQL connection pool:
   - `init_db_pool()`
5. Starts NATS connection and background subscribers:
   - subscribes to `foster.placements` and `agent.*.heartbeat`
6. Starts daily cleanup:
   - `cleanup_old_processed_events()` loop (every 24h)
7. Starts background AFCARS refresh:
   - `background_refresh(interval_seconds=900)`

Also:
- Adds CORS config for frontend dev origins
- Adds routers for REST + WebSockets
- Maintains in-process caches:
  - `_api_latest_placements` used for fast fallback
  - `_agent_heartbeats` used by `/agent/status` endpoint

### 2.2 REST API endpoints (what exists)

#### A) Swarm / Orchestration (Temporal-driven)
In `api/main.py`:
- `POST /swarm/run`
  - Starts Temporal workflow `ArtifexSwarmWorkflow` with input `goal`
- `GET /swarm/status/{workflow_id}`
  - Reads Temporal workflow execution state and optionally final result
- `POST /chat`
  - Starts `ArtifexSwarmWorkflow` for chat question
  - Polls Temporal until completion (max 60s)
  - Returns computed final answer
- `POST /emergent/run`
  - Starts `EmergentSwarmWorkflow`

#### B) Health
- `GET /health`
  - Probes PostgreSQL, NATS, Temporal operator service.
  - Returns per-service status and latency.

#### C) Workflow status summaries and timeline
In `api/main.py`:
- `GET /foster/status/{workflow_id}`
  - Normalizes to `foster-<id>` format
  - Combines data from:
    - `workflow_status` (via `get_workflow_status_db`)
    - `workflow_events` timeline (via `get_workflow_timeline`)
    - latest placement predictions (via `get_latest_prediction`)
  - Returns unified object for the UI tracking page

Also:
- `GET /workflow/{workflow_id}`
- `GET /workflow/{workflow_id}/timeline`
- `GET /workflow/{workflow_id}/progress`

#### D) Referral and event ingestion
In `api/routes/referral.py`:
- `POST /api/referral`
  - Starts Temporal workflow `FosterPlacementWorkflow`
  - Inserts/updates DB for:
    - `children`
    - `placements` (initial pending placement)
    - `active_placements`
  - Publishes a best-effort NATS live event `events.live.child_referred`

- `POST /events`
  - Ingests real-time system events.
  - Deduplicates via `processed_events` table.
  - For `child_referral`:
    - starts workflow, updates children, publishes NATS subject
  - For `close_placement`:
    - marks placements as `closed`
  - For `check_in`:
    - stores check-ins in `check_ins`
  - For all event types:
    - publishes the event to NATS subject `events.{event_type}`

#### E) Dashboard metrics
In `api/routes/dashboard.py`:
- `GET /dashboard/metrics`
  - Postgres-backed counts and last-24h changes
- `GET /dashboard/risk-distribution`
  - Bucket counts by risk score ranges
- `GET /dashboard/events`
  - Recent placement events from DB (with emergency level join)
- `GET /dashboard/workflow-activity`

#### F) Agent heartbeats
In `api/routes/dashboard.py`:

#### G) Placements, approvals, explainability

- `GET /foster/placements`
  - Fetches latest 50 placements using `api/db.py:get_all_placements()`
  - Falls back to in-process cache if DB errors

Internal worker endpoints (not part of public schema):
- `POST /foster/internal/placement`
- `POST /foster/internal/workflow_event`
- `POST /foster/internal/ml_inference_log`

Approval endpoints:

Explainability:

## 3) PostgreSQL DB integration layer (api/db.py)

File: `api/db.py`

### 3.1 Connection pool singleton
- `get_pool()` returns module-level `_db_pool`
- `init_db_pool()` creates asyncpg pool

### 3.2 Data persistence helpers
- `store_placement(placement)`
  - Upsert into `placements`
  - Stores `family_json` and scores/explanations

- `store_workflow_event(workflow_id, stage, status, data)`
  - Inserts into `workflow_events`
  - Upserts into `workflow_status`:
    - updates `progress`, `metadata`, `current_stage`, `status`

- `store_prediction(workflow_id, child_id, recommended, score, confidence, risk_score, feature_importance, top_matches, model_version)`
  - Inserts into `placement_predictions`

- `get_latest_prediction(workflow_id)`
  - Retrieves latest prediction row and parses JSON fields

- `get_workflow_timeline(workflow_id, limit)`
  - Reads `workflow_events` ordered by timestamp

- `get_workflow_status_db(workflow_id)`
  - Reads `workflow_status`

- `get_all_placements()`
  - Joins:
    - `placements p`
    - `workflow_status ws`
    - latest `placement_predictions pp` via LATERAL
  - Parses JSON fields (`family_json`, `recommended`, `feature_importance`, `top_matches`)
  - Normalizes to fields the frontend expects (e.g., `recommended_family`, `foster_family_name`, etc.)

### 3.3 Deduplication helpers
- `is_duplicate_event(event_id)`
  - `processed_events` table with `INSERT ... ON CONFLICT DO NOTHING`
  - fallback to in-memory set if pool is unavailable

- `cleanup_old_processed_events()` deletes processed events older than 7 days

### 3.4 Audit log helper
- `log_action(...)`
  - Fetches previous audit hash
  - Computes new SHA-256 chain hash
  - Inserts into `audit_logs` with `prev_hash` and `hash`

## 4) Integration & data passing (end-to-end flows)

### 4.1 Login flow
Frontend:
- `LoginPage` → `POST /api/login`
Backend:
- validates credentials via `authenticate_user`
- issues JWT via `create_access_token`

HTTP client:
- Axios adds `Authorization: Bearer ...` automatically via interceptor

### 4.2 Referral intake → Workflow start → DB writes → UI updates

Flow:
1. Frontend `ReferralPage` submits form
   - `POST /api/referral`
2. Backend `/api/referral` starts Temporal workflow
   - Temporal workflow id = `foster-{child_id}`
3. Backend writes initial DB rows:
   - `children` upsert
   - `placements` insert `pending`
   - `active_placements` insert `pending_review`
4. Temporal worker/activities run (not fully expanded here due to search limitations), but backend is ready for internal worker endpoints:
   - `/foster/internal/placement`
   - `/foster/internal/workflow_event`
   - `/foster/internal/ml_inference_log`
5. Those internal endpoints call DB helpers:
   - `store_placement`
   - `store_workflow_event`
   - `store_prediction` and others
6. UI reflects changes in two ways:
   - Placements list polling: `GET /foster/placements` (React Query)
   - Workflow tracking polling: `GET /foster/status/{workflowId}` plus WebSocket stream

How timeline and scores are passed:
- Timeline: `workflow_events` → `GET /foster/status/...` → UI timeline rendering
- Scores/explanations: `placement_predictions` → `get_latest_prediction` → UI fields like match/risk/confidence/top_matches

### 4.3 Approval flow (caseworker/supervisor)
1. UI loads pending items:
   - `GET /api/pending_approvals`
2. Caseworker clicks Approve/Supervisor:
   - `POST /api/approve` (caseworker path) OR `POST /api/supervisor_approve`
3. Backend updates DB:
   - `placements.status` and `active_placements.status`
   - may insert into `placement_history` if approved
4. Backend signals Temporal workflow:
   - signals `approve_placement` / `reject_placement`
5. UI updates automatically on next polls:
   - placements polling + dashboard polling
   - workflow tracking polls/WS sees stage/progress changes

### 4.4 WebSocket streaming integration
- Backend WS endpoint reads:
  - `workflow_status` and `workflow_events` every loop
- Frontend establishes WS connection:
  - includes `?token=<jwt>`
- For each incoming JSON message, frontend updates React Query cache:
  - `['workflow-status', workflowId]`
- Then UI rerenders with newest status/progress/timeline/top matches/etc.
